## 上下文

项目已经接入 Umi + React + Tailwind CSS（v4），但目前仅具备基础样式能力，缺少统一的主题令牌与组件实现规范。用户提供了完整的 `The Cognitive Architect` 设计体系，包含色彩哲学、层级规则、排版、深度、组件态与 Do/Don't 约束。  
本次设计需要将该文档转化为项目可执行的主题基础设施，并为后续全部 UI 开发提供统一契约，避免在页面实现阶段重复做风格决策。

## 目标 / 非目标

**目标：**
- 将设计文档中的核心视觉令牌映射为 Tailwind 可复用主题变量（颜色、层级、阴影、圆角、排版、编辑器色板）。
- 建立全局样式入口与主题分层（基础变量层、语义令牌层、组件约束层）。
- 定义组件实现规范，确保按钮、输入框、列表/卡片、浮层、导航与编辑器遵循一致的主题规则。
- 形成可测试、可审查的规范文档，作为后续 UI 评审依据。

**非目标：**
- 本变更不要求一次性重写所有现有页面为新视觉样式。
- 本变更不引入独立设计系统平台（如 Storybook/Token Pipeline 服务）。
- 本变更不处理业务流程、接口契约或数据结构改造。

## 决策

### 决策 1：采用 CSS 变量 + Tailwind 语义映射作为主题承载
- 方案：在 `src/global.css` 中定义 `:root` 语义令牌（如 `--surface`, `--surface-container-low`），并在 Tailwind 层暴露可复用类（通过 `@theme`/主题映射方式）。
- 理由：设计规范强调语义层级（surface tiers），语义令牌比硬编码色值更利于跨组件复用和后续演进。
- 备选：
  - 直接在组件中写固定 hex：实现快，但难维护，无法保证一致性。
  - 仅使用 Ant Design 主题配置：对 Tailwind 工具链覆盖不完整，且不利于统一规范审查。

### 决策 2：以“无分割线”作为默认结构约束
- 方案：在规范中明确禁止使用 1px 实线做分区，优先用背景层级切换表达区块边界。
- 理由：这是 `The Cognitive Architect` 识别度最高的设计特征，属于必须遵循的全局规则。
- 备选：
  - 继续使用传统 border 分区：会破坏目标风格，无法形成“tonal fluidity”。

### 决策 3：将关键组件态标准化为可复用 class/token
- 方案：定义 primary/secondary/tertiary 按钮、输入框默认/聚焦态、卡片层级和浮层阴影规则，统一实现基线。
- 理由：组件层统一后，页面实现成本显著降低，避免“每页一个按钮风格”。
- 备选：
  - 仅做文档约定不做主题初始化：约束无法落地，执行力弱。

### 决策 4：将“所有新 UI 必须对齐规范”作为治理规则写入能力规范
- 方案：在 specs 中使用 MUST/禁止 语义定义强约束。
- 理由：用户明确要求“所有 UI 实现都参照设计文档”，需要规范级硬约束而非建议性说明。
- 备选：
  - 软性建议（should）：无法在评审和验收中形成统一判断标准。

## 风险 / 权衡

- 规范约束较强，初期开发者可能需要适应成本  
  -> 提供可复用 token/class 示例，并在任务中加入验收清单。
- 现有页面与新规范可能短期并存，视觉统一存在过渡期  
  -> 采用“新增/改造页面必须符合，存量页面分批迁移”的策略。
- Tailwind 与 Ant Design 组件并用可能产生样式冲突  
  -> 强制基于语义 token 覆盖，而非散点覆盖具体 DOM 结构。

## Migration Plan

1. 在全局样式层初始化主题变量与 Tailwind 入口映射。
2. 增加主题规范与组件实现规范文件，形成可审查的“单一真实来源”。
3. 先以首页或新模块作为试点应用规范，验证可用性。
4. 对后续页面迭代启用“规范符合性”检查；不符合项在评审阶段修正。
5. 如出现严重兼容问题，可回滚到仅保留 Tailwind 基础能力，不启用强覆盖样式。
